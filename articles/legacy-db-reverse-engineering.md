## はじめに

社内SEとして、卸売業の基幹システム (販売管理システム) の一部を Python に移植する仕事をしました。

このシステムは:

- **336 テーブル、100GB、売上明細だけで 408 万行**
- **外部キー制約はデータベース全体でたった 1 個**
- **現行システムの VB.NET ソースコードは、全体が手元にない**

という状態でした。この記事は、「読めないコードと、読めないスキーマ」を相手に、どうやって仕様を確定させ、Python に移植したかの記録です。

## 何を移植したか

対象は「受注 CSV を販売管理データベースに登録する処理」です。もともとは以下の2段構えで動いていました。

1. **振分け表 Excel (VBA)** — 受注データを営業所・得意先別に振り分ける
2. **frmMain.vb (VB.NET)** — 振分け後のデータを DB に登録する。金額計算・税区分判定・EOS 換算などの業務ロジックがここに詰まっている

この 2 番目の VB.NET 部分を Python に移植し、最終的に **5,489 行の Python スクリプト** (`csv_to_db_v3.py`) として作り直しました。今は Prefect という自動化基盤の上で、10 分間隔のジョブとして動いています。

## 立ちはだかった3つの壁

### 壁1: DB スキーマから業務ルールが読めない

readonly ユーザーで実測したところ、このデータベースは以下の規模でした。

| 項目 | 実測値 |
|---|---|
| テーブル数 | 336 |
| ビュー数 | 106 |
| ストアドプロシージャ数 | 30 |
| データベースサイズ | 100 GB |
| 売上明細テーブル | 408万行 |
| **外部キー制約** | **1 個** |

336 テーブルに対して外部キー制約がほぼゼロ。つまり、**「このテーブルとこのテーブルはこう繋がっている」という情報が、スキーマのどこにも書かれていない**設計でした。

普通、外部キーを見れば「このテーブルは得意先マスタを参照している」「このテーブルの子は明細だ」といった構造がある程度わかります。それが使えないので、**実データを SELECT して突き合わせながら関連を推測する**しかありませんでした。

### 壁2: 現行システムのソースコードが手元にない

移植元の VB.NET コード (frmMain.vb) は、断片的にしか参照できませんでした。関数の一部だけ、画面の一部だけ、といった具合です。

「全部見えないなら移植できないのでは?」と思うかもしれませんが、実際には以下を組み合わせて進めました。

- **見える範囲のコードを読む** — 断片からロジックの type を推測する
- **実データで検証する** — 「この得意先のこの伝票、税抜金額はいくつになっているか」を実際の DB データで確認し、仮説を検証する
- **業務担当者に聞く** — 「このケースって実際どう処理してます?」と現場に聞く。コードより先に、運用でカバーされているルールがあることも多い
- **何度もテストする** — 移植したロジックで計算した結果と、既存システムの実際の結果を突き合わせ、一致するまで仮説を修正する

要するに、**「コードを読む」だけでなく「システムの挙動を科学する」**作業でした。1回の検証で仕様が確定することはほとんどなく、「多分こうだろう」→「実データで試す」→「ズレる」→「原因を仮説修正」のループを何度も回しました。

### 壁3: 既存システムそのものにバグがあった

検証を進める中で、**現行システム側の不具合**もいくつか見つかりました。「正しい仕様」を探しているつもりが、実は「バグの挙動」を仕様だと誤解しそうになったこともあります。

これは地味に怖いポイントです。「今の動きを完全再現する」ことが目的なら、バグもそのまま移植すべきです。しかし業務担当者に確認すると「そこは実は昔から間違っていて、手作業で毎回補正している」というケースがありました。この場合は、**バグを直した上で移植し、業務側に報告する**判断をしました。

「動いているものをそのまま複製する」のと「動いているものを理解した上で正しく作り直す」のは、似ているようで全く違う作業だと実感しました。

## どう設計したか

移植後は、業務ドメインごとに Repository パターンで整理しました。

```
common/sales_db/
├── shohin.py           # 商品マスタ
├── shohin_henkan.py    # 商品コード変換
├── eos_kansan.py        # EOS換算ロジック
├── tanka.py             # 単価計算
└── constants.py         # 定数
```

こうしておくと、「単価の計算式を直したい」ときに `tanka.py` だけ見ればよくなります。VB.NET 時代は 1 つの巨大なフォームクラスに全部書かれていたので、これだけでも保守性が大きく変わりました。

## 学んだこと

- **外部キーがない DB は、実データで関連を推測するしかない。** スキーマだけを眺めていても分からない
- **ソースが全部揃っていなくても移植は進められる。** 断片のコード + 実データ検証 + 現場ヒアリング + 反復テストの組み合わせで、仕様は確定できる
- **「今の挙動を再現する」と「バグも含めて再現する」は違う。** 見つけたバグは、直すか残すかを業務側と相談して決める必要がある
- **移植は「写す」作業ではなく「理解する」作業。** コピーではなく、システムが何のためにその計算をしているのかを理解して初めて、正しく作り直せる
